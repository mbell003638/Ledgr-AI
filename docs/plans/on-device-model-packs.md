# On-device model packs — implementation plan and handoff

**This document is written to be picked up cold.** If you are an AI assistant or a
developer who has never seen this repository or the conversation that produced this
plan, everything you need is here. Do not assume any prior context.

- **Status:** Phase 1 complete and merged. Phase 2 partly done (resume, checksum,
  Wi-Fi guard, wake lock, cancel landed early; manifest still to do). See §4 to
  confirm this yourself rather than trusting this line.
- **Applies to branches:** `codex-sol-on-device-ai` and `Manus-on-device-ai`.
- **Last updated:** 2026-09-05.

**Goal.** Let people run a larger on-device model than Needle when their phone can
take one; choose which pack they want; remove packs they no longer want; and pick up
newer packs without waiting for an APK release.

## 3. Context — read before changing anything

### 3.1 What already works

| Piece | Where |
|---|---|
| Needle 2 inference (voice → tool calls) | `LedgrOnDeviceLlmModule.runNeedle` → `NeedleJni` → `libneedle.a` |
| Receipt OCR, fully on-device | `LedgrLocalOcrModule` (ML Kit text recognition) |
| Pack download with progress events | `LedgrOnDeviceLlmModule.downloadOptional` |
| Pack storage | `filesDir/on-device-models/optional/` |
| Pack listing (installed / eligible / size) | `LedgrOnDeviceLlmModule.listOptional` |
| Pack deletion, including its UI | `deleteOptional`; `advanced-settings.tsx` ~line 699 |

Needle and ML Kit already cover what the app is actually for: speaking a transaction
and scanning a receipt. **Everything in this plan is optional extra capability, not
core function.** That is worth remembering when weighing effort.

### 3.2 What does not work, and why

**Gemma packs can be neither downloaded nor run.** Three independent causes, all
verified 2026-09-05:

1. **No engine.** `frontend/modules/ledgr-native-ai/android/build.gradle` links
   exactly one inference library, `libneedle.a`. `runOptional` throws
   unconditionally (it calls a `gemmaNotWired()` helper).

2. **`libneedle.a` cannot be reused for Gemma.** Cactus's own model card describes
   Needle 2 as *"an open 45M-parameter model … baked into its own engine"* and
   *"self-contained: model baked into the binary, no runtime, no downloads, no
   network."* It is a purpose-built engine for one Simple Attention Network
   architecture, not a general runtime. Its C API
   (`modules/ledgr-native-ai/android/src/main/cpp/include/needle.h`) is also
   **text-only** — `needle_complete(input, max_tokens, out, capacity)` takes no image
   or audio — so the "Scan, native audio" promised for E2B/E4B could not be delivered
   through it even if the weights loaded.

3. **The download URLs never existed.** All three return 404:

   | Requested by the app | Reality on HuggingFace |
   |---|---|
   | `Cactus-Compute/gemma-3-1b-it/…/gemma-3-1b-it.cact` | repo exists, ships `weights/…int4.zip`, no `.cact` |
   | `Cactus-Compute/gemma-4-e2b-it/…` | real repo is `gemma-4-E2B-it` (capital), ships `.zip` |
   | `Cactus-Compute/gemma-4-e4b-it/…` | no such repo; the E4B is `gemma-3n-E4B-it`, which contains **only a README and config — no weights at all** |

   Re-check any time with:
   ```bash
   curl -s -o /dev/null -w "%{http_code}\n" -L \
     https://huggingface.co/Cactus-Compute/gemma-3-1b-it/resolve/main/gemma-3-1b-it.cact
   ```

**Consequence:** `.cact` is a dead end for Gemma. A different runtime *and* a
different weight format are unavoidable. Do not spend time trying to fix the URLs.

### 3.3 Already fixed (do not redo)

RAM eligibility compared `ActivityManager.MemoryInfo.totalMem` against thresholds
written in *advertised* RAM. Android reports less than the phone is sold with, so a
12 GB phone reporting ~11.2 GB fell under the 11 GB bar and Gemma 4 E4B showed
"Hidden on this phone (not enough RAM)". Both the native check and the JS fallback
now round the reported figure up to the nearest size phones are actually sold in
(`advertisedRamBytes`, present in both `LedgrOnDeviceLlmModule.kt` and
`onDeviceTools.ts`).

## 5. Decisions already made — do not re-litigate

### D1. Route by task, not by "which model is smarter"

The instinct to always prefer a downloaded pack because it is more capable is right
for reasoning and **wrong for tool calls**. Needle 2 has grammar-constrained decoding
— a byte-level grammar compiled from the declared tool schemas, so every token is
forced to produce valid JSON matching those schemas — plus a calibrated confidence
head. A general Gemma has neither and will occasionally invent a party, invent an ID,
or emit malformed JSON. In a bookkeeping app that is the worst available failure
mode.

| Task | Order |
|---|---|
| Transactions / tool calls | **Needle first.** Escalate to a pack only when Needle returns nothing or scores below its confidence threshold. |
| Open questions, explanations | **Best installed pack first**, then Needle, then cloud. |
| Scan / vision | **Vision-capable pack only.** Then ML Kit OCR, then cloud. |

### D2. Manifest-driven catalogue (Phase 2)

Replace the hardcoded array with **one manifest URL** in settings, pointing at JSON
hosted with the weights:

```json
{
  "schema": 1,
  "packs": [
    {
      "id": "gemma-3-1b",
      "label": "Gemma 3 1B",
      "rank": 10,
      "url": "https://huggingface.co/<owner>/ledgr-packs/resolve/main/gemma-3-1b-it.task",
      "bytes": 750000000,
      "sha256": "…",
      "minRamBytes": 5905580032,
      "capabilities": ["text", "tools"],
      "runtime": "mediapipe",
      "minAppVersion": 3
    }
  ]
}
```

One change, three requirements answered: link changes need no APK release; a newer
pack is discovered by adding an entry; `sha256` lets a corrupt download be rejected
rather than loaded. Keep the current array as a baked-in fallback for a first run
with no network, and ignore packs whose `minAppVersion` exceeds the running build.

### D3. Host on HuggingFace, not GitHub

Plain Git rejects files over 100 MB. GitHub LFS caps files at 2 GB with paid storage
and bandwidth quotas. Release assets cap at 2 GB, which excludes E2B (2.4 GB) and
E4B (3.8 GB) outright. GitHub also does not want repos used as a CDN.

HuggingFace is purpose-built for weights, free, CDN-backed, and handles multi-GB
files. Keep the repo **public** — a gated repo needs an auth token, which must not
ship inside an app. Gemma's licence permits redistribution but requires its Terms of
Use to travel with the weights; include them in the repo.

### D4. MediaPipe as the runtime

`com.google.mediapipe:tasks-genai` is Google's official Gemma-on-Android API and
arrives as a **Gradle dependency, not a C++ project**, skipping CMake/NDK/ABI work.
Format is `.task`. llama.cpp is the alternative — smaller binary, wider model
support, but the native build becomes yours to maintain.

Put both behind a small `OnDeviceEngine` interface (`load` / `generate` / `close`),
with Needle implementing it too, so this choice is not load-bearing later.

### D5. Multi-slot, deliberately

`LedgrOnDeviceLlmModule.kt` currently deletes every other file in the pack directory
before each download — a single-slot design, defensible when files are 0.7–3.8 GB.
A picker requires multi-slot, so that loop goes (T1). Independently: it currently
deletes a completed multi-gigabyte download **with no warning**, so if single-slot is
ever restored, it needs a confirmation prompt.

### T2 — Rank-based selection

**File:** `frontend/src/accountingV2/onDeviceAsk.ts`


```ts
function selectPack(packs: PackStatus[], needs: Capability[] = ['text']) {

    .filter((p) => p.installed && p.eligible)
    .filter((p) => needs.every((c) => p.capabilities.includes(c)))
    .sort((a, b) => b.rank - a.rank)[0] ?? null;
}
```

## 7. Phase 2 — download robustness

A 2.4 GB download on a phone fails often. Depends on Phase 1.

1. **Resumable** — HTTP `Range` against the existing `.part`, so a dropped connection
   does not restart 2 GB.
2. **Checksum verify** before the `.part` → final rename; delete and report on
   mismatch.
3. **Wi-Fi / metered guard** — the UI already promises "Wi-Fi download"; enforce it.
4. **WorkManager or a foreground service**, so Android does not kill a 20-minute
   download when the screen sleeps.
5. **Cancel button** — there is no way to stop a download today.
6. **Manifest** fetch, parse, cache, `minAppVersion` filtering, and the settings field
   holding its URL (D2).

## 8. Phase 3 — runtime

Needs a real device to verify. Depends on Phase 2.

1. Add `com.google.mediapipe:tasks-genai` to
   `frontend/modules/ledgr-native-ai/android/build.gradle`.
2. Implement `runOptional` with `LlmInference.createFromOptions()` against the
   downloaded path; remove the `gemmaNotWired()` placeholder.
3. **Load one engine at a time** — close the current before opening another; never
   hold two multi-GB models.
4. **Catch OOM at load, not only at download.** RAM eligibility is a static estimate;
   a 12 GB phone under memory pressure can still fail. On failure, mark the pack too
   large for this phone, fall back a tier, and say so plainly.
5. Republish packs in `.task` format and update the manifest.

**Start narrow: MediaPipe with Gemma 3 1B only.** Smallest pack, fits comfortably in
RAM, and it proves the whole chain end to end. E2B and E4B then become extra manifest
entries rather than new engineering.

## 10. Size impact

Weights are **never** in the APK; they download into `filesDir` at runtime. The APK
grows only by the engine.

| Runtime | APK increase, arm64 only |
|---|---|
| MediaPipe `tasks-genai` | roughly +20–30 MB (bundles TFLite and the GPU delegate) |
| llama.cpp | roughly +3–5 MB, but the native build is yours |

`build.gradle` already sets `abiFilters "arm64-v8a"`, so only one ABI is paid for;
adding 32-bit `armeabi-v7a` roughly doubles it. **These figures are estimates and
have not been measured against a real build** — do not quote them as fact.

## 11. Risks

- **Native conflicts.** Needle and MediaPipe both ship native code in one APK.
  Symbol/ABI collision is unlikely but only a build confirms it.
- **Memory.** The real constraint is not download size but whether a 2–4 GB model
  loads on a mid-range phone under pressure. Expect runtime fallback to be needed.
- **Licensing.** Redistributing Gemma weights is permitted but obliges you to carry
  its Terms of Use and use policy.
- **Value.** Needle already handles transactions; ML Kit already handles scanning.
  Packs add open-ended reasoning quality, not core function — weigh that against
  ~25 MB of app size and a second runtime to maintain.

### 12.2 Frozen bridge contract

This is the interface between the two halves. **Neither agent may change it
unilaterally.** It is the current shape, verified 2026-09-05, and both sides code
against it.

Native module methods (`LedgrOnDeviceLlm`), as consumed in

```ts
export type OptionalModelStatus = {
  id: OptionalOnDeviceModelId;

  eligible: boolean;

```

Event `downloadProgress` payload: `{ id: string, received: number, total: number }`.

**Rules**

- Agent B may add *optional* fields to `OptionalModelStatus` (for example

- Agent A treats every field as possibly absent — an older native build may not send
  new ones.
- `rank` and `capabilities` are **catalogue** data owned by Agent A, not native data.
  Agent B must not add them to `listOptional`.
- Any change to this contract requires editing this section first, in its own commit,
  agreed by both.

### 12.3 Branches and merge order

Two agents must not share a working tree. Each works on its own branch off the same
base:

```bash
BASE=codex-sol-on-device-ai
git switch -c packs/js-selection    $BASE   # Agent A
git switch -c packs/kotlin-download $BASE   # Agent B
```

Merge **Kotlin first**, then JS:

1. Agent B merges `packs/kotlin-download` into `$BASE`. It is leaf code — nothing in
   the JS layer imports it — so it lands without touching Agent A's work.
2. Agent A rebases `packs/js-selection` onto the updated `$BASE`, re-runs the §2.3
   gates, then merges.
3. Cherry-pick the combined result to `Manus-on-device-ai` (clean — see §2.2), and
   re-run the gates there.

Expect **no conflicts** if §12.1 was respected. If you hit one, that means someone
edited a file they did not own; resolve by reverting the trespass, not by merging it.


**Compilation.** There are **no Kotlin tests in this repo** — `frontend/__tests__` is
jest/JS only. The only automated proof Kotlin compiles is the Android build, so it
must have run green at least once. State the run and its result in the handback.

**Contract.** `git diff $BASE -- frontend/src/` must be **empty**. Agent B touching
any JS file is a contract breach.

**Behaviour checklist:**

- [ ] T1: the `optionalDir().listFiles()` wipe loop is gone; two packs can be
      installed simultaneously and both report `installed: true`
- [ ] T1: free-space guard rejects a download that will not fit, counting **both**
      the `.part` and the final file, with a message naming the shortfall
- [ ] The `.part` → final atomic rename still happens **last**, after any checksum
      verification — a partial file must never be visible as installed
- [ ] Resume: an interrupted download continues from the existing `.part` via HTTP
      `Range`, and a server that ignores `Range` restarts cleanly rather than
      appending to a stale file and corrupting it
- [ ] Checksum failure deletes the `.part` and surfaces a clear error — it must not
      leave a corrupt file installed
- [ ] Cancel leaves no stale `.part` behind, and cancelling twice does not throw
- [ ] Wi-Fi/metered guard blocks a metered download with an actionable message
- [ ] `downloadProgress` still emits `{id, received, total}` unchanged (§12.2)
- [ ] `deleteOptional` removes only the named pack, never a sibling

**Device checks** — these cannot be verified by review or CI; run them on hardware
and say plainly if you did not:

- [ ] a real interrupted download resumes rather than restarting
- [ ] a download survives the screen going off (WorkManager / foreground service)
- [ ] a 2 GB+ download completes and the pack shows as installed

### 12.5 What the audit will and will not catch

The reviewing agent can verify statically: contract adherence, the §4 state commands,
the three gates, the checklist above by reading the diff, and the specific failure
modes listed there.

It **cannot** verify device behaviour — resume across a real dropped connection, doze
survival, or memory pressure. Those depend on the phone. Any handback that claims
them without having run them on hardware should say so explicitly rather than imply
otherwise.
